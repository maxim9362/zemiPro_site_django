## 2. Защита от повторного добавления

В ветке `stage-00-audit` расширены ignore-шаблоны для распространённых локальных секретов, SQLite/DB и контейнеров ключей. Однако `.gitignore` **не удаляет уже отслеживаемые** файлы из PSEO и **не чистит Git history**. Текущий PSEO-репозиторий и рабочие данные намеренно не изменялись.

Для будущей приёмки рекомендована локальная проверка секретов по текущему дереву и истории (например, Gitleaks в изолированном окружении), с выводом только путей и классификации, без строк/материалов из секретов. Уровень доступа и запуск согласовать отдельно. Не пытаться проверять действительность чужих ключей через API без явного разрешения.

## 3. Порядок безопасной обработки владельцем (не выполнялся)

1. Определить, какие аккаунты/сервисы используют отслеживаемые конфиги и какие ключи могут быть действующими. Значения не присылать в чат и не публиковать в PR.
2. Сначала создать/проверить резервные копии нужного контента и баз (00.3), закрыть доступ посторонним, проверить разрешения на репозиторий.
3. Отозвать или ротировать **действующие** ключи через соответствующие сервисы; новые значения разместить только в менеджере секретов или переменных окружения, не в Git.
4. Удалить чувствительные файлы **из отслеживания** без стирания нужных локальных копий (например, `git rm --cached`, но только после backup и явного согласования), настроить `.gitignore` PSEO.
5. Историческое удаление секретов — отдельный план, поскольку rewrite/force-push влияет на все клоны, PR и ссылки. Даже после очистки истории ключи, однажды опубликованные в Git, следует считать раскрытыми и отозвать.
6. После разрешённой ротации выполнить **санитизированный** повторный аудит: итоговые статусы `PASS/FAIL/SKIP/NOT_RUN` и список оставшихся блокеров, но не значения ключей.

## 2026-11-10 — углублённый аудит 00.2 и устранение секретного литерала

**Подтверждение высокого риска:** в **публичном** Django/legacy-репозитории `admin_bot/admin_main.py` ранее находилась строка `PROXY_URL` с SOCKS5 URI, включавшим учётные данные (`user:password@host`). Значение не включено ни в этот отчёт, ни в журнал; его действительность **не проверялась**. В рабочей ветке `stage-00-audit` литерал заменён чтением `ADMIN_BOT_PROXY_URL` из переменной окружения, с прямой сессией `AiohttpSession` при отсутствии прокси. **Ни production, ни работающий Telegram-бот не обновлялись.** В старых Git-коммитах значение сохраняется; требуется отзыв/смена пароля у провайдера прокси даже после merge.

**Метаданные истории PSEO:** без открытия файлов или просмотра значений проверены деревья 6 исторических коммитов (май 2026). Отслеживаемые `.env` и `index_site/service_account.json` обнаружены во всех 6, бинарные SQLite — в части ревизий; прошлый `customer_admin_write.db` также присутствовал в истории. Это не полный поиск всех секретов в истории. Сервисная учётная запись может быть действующей; **проверка статуса и отзыв её ключа требуют владельца и доступа к провайдеру**.

**Ограниченный обзор исходников:** проверены безопасные Python-файлы основного репозитория и PSEO на явные маркеры. Найдена приведённая выше жёсткая строка прокси; прочие явные литералы в выбранных исходниках не обнаружены. Это не доказывает отсутствия других секретов. Содержимое `.env`, JSON-ключей и SQLite не читалось.

**Создана инструментальная проверка:** `scripts/stage00_secret_audit.py` работает локально с `git ls-files`, позволяет `--history-paths` (только имена файлов по истории Git) и анализирует доступные текстовые исходники на маркеры, возвращая **только тип, путь и номер строки**, без содержимого. `scripts/tests/test_stage00_secret_audit.py` — 6 проверок на синтетических данных, локально `6/6 PASS`; полный Git checkout/скан всей истории в реальном окружении **NOT_RUN**.

3. Проверить все потенциально действующие токены в PSEO `.env` и заменить/отозвать через соответствующих провайдеров. Список сервисов определять владельцу без передачи значений в чат.
