# ZemiPro — 00.5: архитектурная карта и план перехода без legacy data import

**Дата:** 2026-11-11
**Статус:** `DONE / DOCUMENTED_AND_SYNTHETICALLY_VERIFIED`
**Решения:** [ADR-0001](DECISIONS/ADR-0001-DJANGO-ONLY-NO-TELEGRAM.md), [ADR-0002](DECISIONS/ADR-0002-REBUILD-WITH-URL-ONLY.md), [ADR-0003](DECISIONS/ADR-0003-DJANGO-ONLY-SINGLE-DATABASE.md).  
**Источники:** `zemipro_web/apps/*/models.py`, `apps/marketplace/services.py`, `core/urls.py`, `marketplace/migrations/0003_require_order_owner.py`, `zemipro_web/docker-compose.django.yml`, `docs/SEO_URL_INVENTORY.csv`.  
**Область:** проектирование, независимый обзор и synthetic PostgreSQL dry-run; реальные данные и production не читались и не изменялись.

## 1. Целевая схема

```text
Клиент (ПК / мобильный)           Исполнитель (ПК / мобильный)
             └───────┬───────────────┘
                     ▼
              Django routes / auth
                     ▼
          Views / forms / future REST API
                     ▼
          Доменные Django services
                     ▼
                Django ORM
                     ▼
             PostgreSQL (одна БД продукта
             на каждое отдельное окружение)
              ├─ accounts: User, ClientProfile, WorkerProfile
              ├─ marketplace: Category, Subcategory, Order, Response, Rating
              ├─ locations: City
              ├─ notifications: Notification
              ├─ moderation: Complaint
              ├─ analytics: GlobalStats, CategoryStats
              └─ будущие чат/SEO-модели (после отдельных этапов)

Отдельно, не часть runtime:
  Telegram/asyncpg -> только архив и проверка секретов; НЕТ импорта
  Flask/PSEO/SQLite -> только перечень известных публичных URL
  Старые /master/... -> REVIEW -> будущий точный 301/KEEP/404/410
```

*Новый API и чат будут обращаться к тем же сервисам и PostgreSQL, а не к отдельным автономным сущностям.*

## 2. Фактические отношения и ограничения текущего кода

| Объект / зависимость | Сейчас в Django | План / условие |
| --- | --- | --- |
| `accounts.User` | `AbstractUser`, единственный `AUTH_USER_MODEL`, `role` — один выбор, `telegram_id` nullable | Переиспользовать пользователя; многоролевая логика 03.1; не использовать Telegram ID для нового входа |
| `ClientProfile.user`, `WorkerProfile.user` | `OneToOne(User)` | Один аккаунт может иметь профили; права и UX надо проверить в 03 |
| `WorkerProfile.skills` | ManyToMany `Category` | Сохранить связи, проверить каталожные фильтры и варианты подкатегорий 02/05 |
| `Category.slug`, `City.slug` | Unique | Использовать стабильные доменные ключи; создание/обновление без дубликатов по slug |
| `Subcategory` | `unique(category,slug)` | Никогда не сливать одинаковые slugs из разных категорий без контекста |
| `Order.client` | FK `PROTECT`, NOT NULL после миграции 0003 | Обязательный авторизованный владелец; legacy с `client=NULL` требует отдельного решения, без auto-fix |
| `Order.category`, `Order.city` | FK `PROTECT`; `subcategory`/назначенный `worker` nullable | Сохранять ссылки и реальные данные, избегать ручного изменения PK |
| `Response` | `unique(order,worker)`; один мастер один отклик на заявку | Транзакционный выбор одного исполнителя через `select_for_update()` сохраняется |
| `Rating` | OneToOne с `Order` | Только подтверждённый заказ; фиктивные отзывы не импортировать |
| `Notification` | FK на пользователя; ссылки на `Order` и `Response` | In-app уведомления; email по следующему этапу, Telegram исключён |
| `Complaint` | FK на автора, опциональные `User`, `Order`, `Rating` | Объектные права и модерация проверяются отдельно |
| `apps.seo` | Модели/представления — заглушка; URLconf пуст | Новые собственные Django SEO-страницы на этапе 08, без PSEO-кода |

Пробелы архитектуры, **не исправляемые в 00.5**: многоролевая модель (`role`), безопасный чат, подтверждение контакта, полное SEO, публичный API, политика `is_blocked`. Уточнять в 03, 07, 08 и 10.

## 3. Матрица источников и целевых сущностей

Машиночитаемая запись: `docs/STAGE_00_SOURCE_TARGET_MATRIX.csv`. Главное правило: **`REUSE` относится только к текущему Django-коду/данным, а не к импорту старых баз**.

| Источник | Цель | Правило |
| --- | --- | --- |
| Существующая схема Django | Django PostgreSQL, те же `accounts.User`, `Order`, `Response`, `Rating` и связанные модели | `REUSE` через Django migrations; подтвердить состояние фактической БД до операции |
| Django каталожные seed-команды | `Category`, `Subcategory`, `City` | `ADAPT` в 02: единый утверждённый набор и RU/EN/HE, идемпотентность по slug |
| Старый Telegram PostgreSQL | **НЕТ** | `REJECT` импорт/синхронизацию и восстановление для новой платформы |
| Старый PSEO SQLite и Flask | **НЕТ** | `REJECT` базу/тексты/обработчики/маршруты как исполняемый код |
| `docs/SEO_URL_INVENTORY.csv` | Контрольная карта old URL → новый Django URL | `REVIEW`: только после GSC/HTTP и семантического соответствия, не импортировать как контент |
| Новая регистрация, заявки и профили пользователей | Одна схема Django | Только новые записи через авторизованный workflow и защищённые сервисы, без создания фейковых пользователей/заказов |

Никакого `legacy_id`/сопоставления `user_id` Telegram и PSEO с Django не нужно: **источники не импортируются**. Если владелец в будущем изменит решение, это будет отдельное согласование схемы `source_system/legacy_id/import_batch`, сохранности данных, dry-run и миграционного PR — не скрытая функциональность 00.5.

## 4. Безопасный dry-run (план, а не выполненный импорт)

**4.1. Существующая Django-БД (только после разрешения)**

1. Зафиксировать источник, версию PostgreSQL, версию Django/migrations, схему/таблицы и агрегированные counts без PII.
2. Выполнить проверенную резервную копию и восстановить её **только в отдельной среде**; обеспечить контроль размера, SHA-256, counts и версий (см. 00.3).
3. На клоне запускать `showmigrations`, `makemigrations --check`, `migrate --plan`, `migrate` с целевым SHA. Заранее проверить `0003_require_order_owner`: при `client=NULL` **остановиться**, не назначать фальшивого владельца.
4. Сравнить количество `User`, `Category`, `Subcategory`, `City`, `Order`, `Response`, `Rating`, `Notification`, `Complaint` до/после. Без массовой пересоздачи PK, владельцев и заказов.
5. Идемпотентный повторный прогон в изолированном окружении: количество данных не должно расти без причины; соответствие внешних ключей, уникальности и статусов подтверждено.
6. При расхождении — `FAIL / BLOCKED`; схему/данные production не трогать.

**4.2. Новый чистый инстанс Django**

- Инициализировать пустую PostgreSQL через Django migrations и одобренные seed-команды; добавить только реальные регистрации/заказы после запуска. Не копировать старый Telegram/PSEO.
- Синтетические данные и fixture-аккаунты держать в test/staging, не в публичном каталоге.
- Файлы `zemipro_web/core/settings.py` в `main` и раздельные settings из ветки `stage-01-stabilization` различаются; для дальнейшего деплоя использовать прошедшую приёмку конфигурацию 01.1, а не дублировать её.

**4.3. Старые URL (не импорт данных)**

- На входе CSV с 21 выборочно найденным адресом; `http_status`, индекс, показы, клики и целевые Django URL ещё `UNVERIFIED`.
- Для каждой строки: `old_url` уникален; `target_new_url` назначается только при существующей релевантной новой странице, после ручного решения; валидировать домен/HTTPS, конечный код, отсутствие redirect-chain, циклов, «всё на главную», коллизий canonical/hreflang.
- Группа `lachish` и `center` — **региональные слуги**, а не города. Нельзя автоматически сопоставлять `/master/lachish/...` с Ашдодом или `/master/center/...` с одним городом: сначала проверить семантику и новые категории.
- Статус до проверки — `REVIEW`. Ни одного `301` не публиковать до утверждённой таблицы переходов и rollout этапа 08.
- Запись о каждом решении: исходный URL, целевой URL/KEEP/404/410, источник доказательства, причина, дата согласования, test result.

## 5. Порядок реализации и первый деплой

1. **Завершить этап 00:** secret handling (00.2), подтверждённый backup/restore (00.3), приёмка URL inventory (00.4), диагностика 00.6. До этого никакого production/deploy/удаления архивов.
2. **Этап 01:** сохранить рабочие изменения `stage-01-stabilization`; изолированные development/test/staging, миграции, CI, backup, базовые показатели. Синхронизацию веток выполнять без переписывания истории и без PR merge без владельца.
3. **Этапы 02–07:** каталог, география, локализация RU/EN/HE, роли и профили, заказ/отклики, защищённый чат/уведомления/отзывы. Один Django backend и единая бизнес-логика для мобильных и ПК интерфейсов.
4. **Staging:** отдельные PostgreSQL/media/secrets, HTTPS, минимальные права, синтетические данные и пройденный полный тестовый цикл; копирование рабочей БД в staging не разрешено автоматически.
5. **Этап 08:** завершить новые Django SEO-страницы, получить GSC и полноту старых URL, подготовить и протестировать точечные redirects; согласовать домен/Cloudflare/SEO cutover. Старый Flask не переводить в новую архитектуру.
6. **Переход на публичный сайт:** только отдельное разрешение владельца, проверенный backup и dry-run, rollback, наблюдаемость и сценарии smoke. Не менять DNS или текущий сайт в рамках архитектурной документации.
7. **Rollback:** записать исходные DNS/Cloudflare/маршрутизацию и старую рабочую версию, подготовить восстановление БД/медиа; для несовместимых миграций — заранее обоснованный forward-fix или restore отдельной проверки. Не выполнять опасный автоматический откат SQL.
