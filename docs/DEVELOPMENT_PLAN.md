## 1. Продукт и границы разработки

**ZemiPro** — универсальный многоязычный маркетплейс услуг для Израиля, ориентированный по механике на [Profi.ru](https://profi.ru/). Заказчик ищет специалиста в каталоге **или** публикует заказ; специалист получает релевантные заявки, отправляет предложение, общается с клиентом, выполняет работу и получает подтверждённый отзыв.

**Фиксированные решения:**

- **Технологическая база:** существующий Django-проект + PostgreSQL. Не начинать новый проект без необходимости.
- **Все категории услуг:** ремонт, строительство, уборка, образование, IT, перевозки, красота, спорт, события, животные, автомобили, деловые и другие услуги. Каталог расширяем через данные, не изменяя ядро.
- **Языки:** `ru`, `en`, `he`, включая полноценный иврит RTL; для контента — оригинал и опциональный перевод.
- **География:** долгосрочная архитектура охватывает Израиль; **единственный город первого публичного пилота — Ашдод** (уточнение владельца 2026-11-12, заменяет прежние предложения пилота на нескольких городах). Другие города пока не должны выглядеть обслуживаемыми и не должны принимать заявки.
- **Продукты:** сначала полноценный адаптивный веб-сайт, затем Android/iOS на **том же Django API**.
- **Монетизация:** бесплатная публикация заказов и базовый доступ мастеров на запуске; платные функции только после оценки реального спроса.
- **Профессиональные лицензии:** платформа **не вводит обязательную проверку документов при обычной регистрации**. Не создавать неподтверждённый бейдж «проверен». Законодательные ограничения по видам услуг сохраняются.
- **Платежи за работу:** напрямую между заказчиком и исполнителем на первых релизах; ZemiPro не держит деньги клиентов.
- **ИИ:** Gemini для вспомогательных функций, не критическая зависимость сайта; Codex — для разработки системы, а не постоянный фоновый исполнитель задач.
- **Маркетинг:** Facebook и SEO; автопубликации только через официально поддерживаемые каналы, без спама и обмана.

**Не копировать** у Profi.ru торговую марку, дизайн один в один, тексты, код, изображения и чужие материалы. Сайт — источник идей о сценариях, а не исходных компонентов.

## 2. Правила работы Codex и статусы

### 2.1. Регламент поставки

**Утверждённый процесс:** GPT в ChatGPT реализует все подэтапы в существующей ветке этапа, выполняет адресные доступные тесты и обновляет документацию. После завершения всего этапа Codex Cloud проводит независимую итоговую проверку кода, ТЗ, архитектуры, безопасности, Django/PostgreSQL migrations, интеграционных/регрессионных тестов и Docker/configuration по требованиям этапа. Ошибки исправляются в той же ветке, после чего Codex повторяет необходимые проверки. Полный аудит перед каждым подэтапом не выполняется.

1. **Один этап = одна рабочая ветка = один итоговый PR**, если владелец не разрешил исключение. Подэтапы выполняются последовательно внутри этапа, с промежуточными коммитами.
2. Перед началом этапа изучать `AGENTS.md`, основное ТЗ, этот документ и **только релевантные файлы**, а не перечитывать весь репозиторий без причины.
3. Перед разработкой функции проверять существующий Django; старые Telegram/PSEO не использовать как поставщиков данных. Решение: `reuse/adapt/rewrite/reject` с обоснованием.
4. По завершении **каждого подэтапа** обновлять таблицу прогресса, затронутые `REQ-*`, результат тестирования и ограничения. Не ждать окончания всего этапа для обновления документации.
5. На подэтапе GPT запускает адресные доступные тесты; после всех подэтапов Codex Cloud выполняет независимый этапный набор по риску. Не скрывать неисполненные тесты.
6. Не менять схему production-БД без миграции, проверенного backup, dry-run/репетиции и разрешения владельца. Развёртывание staging и production — разные операции.
7. Не коммитить ключи, реальные контакты, пароли, данные платежей и пользовательские переписки. Все внешние публикации, массовые сообщения, платежи, удаление данных и объединение PR требуют явно предусмотренного разрешения.
8. Если выполнение подэтапа невозможно — пометить `BLOCKED` с причиной, не считать его `DONE` и не закрывать гейт этапа обходом.
9. Codex не должен самостоятельно менять выбранную пользователем модель и режим reasoning; эти настройки остаются за владельцем.

### 2.2. Статусы и Definition of Done

- `NOT_STARTED` — не начат.
- `IN_PROGRESS` — есть рабочие изменения, но критерии ещё не выполнены.
- `BLOCKED` — есть зафиксированный блокер/внешняя зависимость.
- `REVIEW` — код готов, проходит проверку/PR.
- `DONE` — подтверждены критерии и тесты, документирован результат; этап закрыт после принятия PR.
- `DEFERRED` — сознательно отложен отдельным решением, с указанием релиза и последствий.

**Общий DoD каждого подэтапа:** реализованы указанные задачи; учтены объектные права, приватность и языки, где это применимо; тесты добавлены и выполнены либо честно обозначен блокер; документация обновлена; изменены только согласованные файлы; указаны известные риски и способ отката, если есть миграция.

**Соглашение о статусах:** все этапы и подэтапы ниже изначально имеют `NOT_STARTED / требуется аудит`. Старый код может покрывать часть требований; нельзя автоматически ставить `DONE` без проверки и тестов. После этапа 00 провести честную переоценку статусов.

### 00.1. Инвентаризация существующих реализаций

## ЭТАП 01. Стабилизация Django, базы и окружения

**Цель:** сделать существующий Django надёжной, безопасной и воспроизводимой основой дальнейших этапов.

**Порядок старта:** реализация этапа 01 ведётся через GPT в ChatGPT, итоговая независимая проверка — через Codex Cloud после всех 01.1–01.6. ### 05.5. Публичные анкеты, избранное и пустые состояния

- SEO-дружественная анкета с портфолио, услугами, регионом и только допустимыми контактами.
- Избранное и ссылки на похожие услуги; когда нет мастеров, предлагать создать заявку без выдуманных результатов.
- **Приёмка:** нет фальшивых карточек, просроченных приглашений и приватных контактов в публичных метаданных.

### 05.6. Скорость и UX поиска

- Проверить N+1 запросы, пагинацию, индексируемые/неиндексируемые комбинации фильтров, mobile/RTL.
- **Приёмка:** фиксируется измеряемый baseline, у фильтров корректные пустые и ошибочные состояния.

**Гейт 05:** оба пользовательских пути (заказ → исполнители и каталог → конкретный исполнитель) работают независимо и безопасно.

## ЭТАП 06. Предложения, договорённости и назначение исполнителя

**Цель:** специалист откликается, клиент сравнивает условия и безопасно выбирает одного исполнителя.

**Требования:** `REQ-OFF-001–007`, `REQ-ORD-007–008`, `REQ-DATA-004`.

### 06.1. Модель предложения и история изменений

- Использовать существующий `Response` как источник совместимости; расширить до предложения с ценой/диапазоном, сроком и статусами `sent/viewed/negotiating/accepted/rejected/withdrawn/expired`.

- **Приёмка:** невозможно создать дубли активных откликов или подменить чужую цену.

### 06.2. Кабинет клиента и сравнение предложений

- Список откликов с профилем, ценой, сроками, текстом, рейтингом и действиями «обсудить/отклонить/выбрать».
- Языковые и мобильные интерфейсы, сортировка, доступные фильтры, чёткое отображение договорной цены.
- **Приёмка:** клиент видит несколько реальных предложений, но не получает закрытые данные других заказов.

### 06.3. Атомарное назначение специалиста

- Серверная транзакция с блокировкой строки/условными обновлениями; назначение одного исполнителя для одиночного заказа.
- Повтор клика, две параллельные операции и отозванное предложение должны давать корректный конечный статус.
- **Приёмка:** concurrency test доказывает, что два исполнителя не назначаются одновременно.

### 06.4. Фиксация договорённостей

- Сохранить согласованные условия: цена/метод расчёта, срок, важные детали, автор/время подтверждения.
- Изменения после согласования — через явно видимую историю с уведомлением второй стороны, а не тихое редактирование.
- **Приёмка:** обе стороны видят согласованную версию условий, журнал позволяет восстановить изменения.

### 06.5. Исполнение, завершение и спорные случаи

- Начало работ, завершение по подтверждению, отмена и сообщения о проблеме; при споре — статус и передача модератору.
- Не закрывать заказ автоматически как «выполнен» из-за истечения таймера.
- **Приёмка:** завершение доступно только уполномоченным сторонам и корректно открывает возможность отзыва.

### 06.6. Антифрод и аудит событий заказа

- Отслеживать злоупотребления откликами, резкую массовую рассылку, подмену статусов и попытки доступа к чужим предложениям.
- **Приёмка:** тесты права доступа, идемпотентности и последовательности событий прошли.

**Гейт 06:** рабочий сценарий «два отклика → обсуждение условий → один выбранный мастер → завершение», без гонок и потери истории.

- Отзыв разрешён заказчику только на соответствующий завершённый заказ; один отзыв на единицу договорённости по утверждённой модели.

- **Приёмка:** нельзя отозваться на чужой/несуществующий заказ, создать накрученные отзывы или изменить рейтинг через API.

### 07.5. Жалобы и административная модерация

- Переиспользовать `apps/moderation`: причины, статусы, очередь, блокировки, журнал действий, уведомления, апелляции.
- Доступ модератора ограничен необходимым, чувствительные действия аудируются; конфликтные случаи эскалируются человеку.
- **Приёмка:** жалоба из карточки мастера, заказа и чата поступает модератору и закрывается с зафиксированным исходом.

### 07.6. Перевод переписки и AI-подсказки

- Интегрировать Gemini как **необязательную** опцию перевода и улучшения текста; исходник сообщения никогда не затирается.
- Не пересылать без необходимости личные номера, адреса, секреты, закрытые вложения; учитывать согласия и лимиты.
- **Приёмка:** кнопка «Показать оригинал» работает, а при недоступности Gemini чат продолжает функционировать.

### 07.7. Сквозные E2E-тесты двух ролей

- Пройти оба сценария: публикация заявки и прямое приглашение → предложение → чат → выбор → завершение → отзыв.
- Проверить RU/EN/HE, телефоны и суммы в RTL, недоступность AI, блокировку пользователя и запрос чужого объекта.
- **Приёмка:** e2e-чеклист проходит в staging с синтетическими пользователями; критичные баги закрыты.

**Гейт 07:** end-to-end marketplace работает без ручного исправления данных, закрытые сообщения защищены, отзывы и жалобы привязаны к реальным событиям.

## ЭТАП 09. Новая Django SEO-система и безопасное переключение сайта

**Цель:** создать SEO-страницы нового Django-маркетплейса и принять точное решение по каждому подтверждённому legacy URL без импорта старого кода или контента.

### 09.2. Создание новых SEO-страниц и проверка соответствия URL

- Создавать новые SEO-страницы на основании актуальных Django `Category`, `Subcategory`, `City` и реальных профилей; никакого импорта PSEO/SQLite/Flask/старых текстов.
- Для каждого значимого старого URL определить только тематически соответствующую новую страницу и решение KEEP/301/404/410 по фактическим доказательствам.
- Проверить новые Django migrations/seed и URL-матрицу на дубли, redirect loops, корректность canonical/hreflang и план отката. Старый PSEO не импортировать.

### 09.3. SEO-страницы в Django

- Реализовать страницы раздела, услуги, города, услуги в городе и анкеты мастера на общей модели данных.
- Добавить уникальные title/description, хлебные крошки, полезный контент, связанные услуги/города, обоснованные CTA.

### 09.4. Техническое SEO и три языка

- **Приёмка:** для репрезентативной выборки URL нет конфликтов canonical/hreflang и некорректных schema.org утверждений.

### 09.5. Страница-по-странице миграция и редиректы

- Реализовать `SeoLegacyUrl`/реестр маршрутов и индивидуальные 301/308 на смысловые аналоги; исключить цепочки и циклы.

- **Приёмка:** тесты на все существенные URL, нулевые критические редирект-циклы и понятный rollback.

### 09.6. Переход на Django и контроль индексации

- Переключить production только после backup, smoke tests, прав доступа и отдельного разрешения владельца.
- Сравнить HTTP-статусы, sitemap, 404, индексирование, органический трафик, конверсию по ключевым страницам; держать rollback-план.
- **Приёмка:** основной домен открывает Django-продукт; legacy SEO-доступность подтверждена, ошибки мониторятся.

### 09.7. Редакционный конвейер нового SEO-контента

- Контент создаётся по спросу и реальным данным: бриф → черновик (опционально Gemini) → фактчекинг/дубли → локализация → публикация → замер.

- **Приёмка:** у публикаций есть источник данных, версия, статус ревью и контроль низкоценного контента.

**Гейт 09:** подтверждённые legacy URL учтены, полезные страницы работают в Django, решения KEEP/301/404/410 проверены, переключение публичного домена подтверждено безопасным тестированием.

- **Приёмка:** безопасность и метрики проверены, ошибки/дубли контролируются, основной marketplace не зависит от работы раздела знаний.

### 14.8. Личные рекомендации мастеров — отдельно от отзывов

- Спроектировать модель рекомендации от зарегистрированного пользователя о личном опыте работы вне ZemiPro; отдельно от Rating и подтверждённых заказов. Автор указывает контекст услуги, но ZemiPro не выдаёт такой опыт за проверенный факт.
- Показать в профиле отдельную секцию личных рекомендаций с понятной пометкой; запретить влияние на рейтинг подтверждённых заказов. Модерация, жалобы, антиспам, дубли, приватность и удаление по правам.
- **Приёмка:** внешний опыт и отзыв по заказу не смешиваются; нельзя подделать автора, накрутить рейтинг или раскрыть контактные данные.

### 14.9. Кнопка «Поделиться в Facebook» в профиле мастера

- Использовать только публичную ссылку, безопасный OpenGraph-предпросмотр, добровольное действие пользователя; fallback «Скопировать ссылку». Без Facebook Login, автопостинга или чтения чужих групп.
- Проверить поведение на RU/EN/HE, мобильных устройствах и при отсутствии приложения Facebook.
- **Приёмка:** мастер и пользователь могут добровольно поделиться профилем без раскрытия PII и без автопубликаций.

### 14.11. Публичный запрос «Посоветуйте мастера» (после проверки спроса)

- Отдельный от «Спросить мастера» и обычного Order сценарий: категория, город, публичное описание без адреса/телефона, ответы с личными рекомендациями и ссылками на профили.
- Реализация обязательна; публичное включение только после подтверждённого спроса и отдельного `GO` владельца. Обязательны модерация, жалобы, защита от саморекламы и дублирования. Переход к заказу — явное действие клиента.
- **Приёмка:** запрос не создаёт заказ, не показывает скрытые контакты, не искажает рейтинг мастера, проходит проверки RU/EN/HE, RTL и безопасности.

### 14.12. Кнопка «Пригласить мастера в ZemiPro»

- Дать пользователю возможность пригласить известного ему **не зарегистрированного** мастера: сформировать безопасную ссылку регистрации, которую человек сам отправляет через Facebook/Messenger или другой выбранный канал, либо копирует.
- Специалист регистрируется самостоятельно; не импортировать телефонную книгу/друзей, не создавать фальшивые профили; не смешивать с приглашением зарегистрированного мастера на Order (этап 05).
- **Приёмка:** добровольная ссылка работает и учитывается в агрегированной аналитике, без массовых рассылок, утечки контактов и обязательного Facebook Login.

**Гейт 14:** каждый из 14.1–14.12 реализован, проверен и принят по своим критериям. Публикация Q&A и «Посоветуйте мастера» управляется отдельными `GO` и feature flags; `NO-GO` не означает `DEFERRED` разработки. Ранний MVP и этапы 11–13 независимы, но общий `DONE` программы требует закрытого этапа 14. Для реализации этапа — отдельная ветка и один итоговый PR.

## 4. Сквозные требования, обязательные на всех этапах

### 4.1. Безопасность и законодательство

- Любые данные/вложения доступны только по серверным правам; запрещены IDOR и массовое раскрытие телефонов/адресов.
- Профессиональные документы **не проверяются обязательно** при регистрации, но реальные юридические ограничения для регулируемых услуг подлежат соблюдению; нельзя рекламировать статус «лицензирован/проверен» без доказательства.
- Не сохранять в аналитике секреты, полный адрес, номера телефонов и личную переписку. Согласия, сроки хранения, удаление/экспорт — через документированную процедуру.
- Обновить правила пользования, политику приватности, порядок жалоб и раскрытие рекламных материалов на всех трёх языках перед полноценным запуском.

### 4.2. Языки и UX

- Каждый новый публичный пользовательский сценарий и системное сообщение реализуется на `ru`, `en`, `he`, проверяется на смартфоне.
- Хранить исходный язык пользовательского контента; автоматический перевод опционален и отмечен.
- Никакие RTL-правки не должны ломать LTR для сумм, телефонов, email и ссылок.

### 4.3. Данные и качество

- PostgreSQL Django — единственная транзакционная БД каждого окружения. Старые SQLite PSEO и PostgreSQL Telegram не импортировать.
- Миграции обратимы где возможно; каждая миграция с данными имеет backup/dry-run, идентификаторы источника и сверку количеств.
- Запрещены фиктивные отзывы, придуманные мастера, ложные количества заказов и подменённые рейтинги.
- Использовать unit, integration, object-permission, concurrency, e2e и smoke проверки по риску.

### 4.4. Маркетинг

- Органический Facebook и SEO — основные каналы стартового роста, без обязательного бюджета на рекламу.
- Кодекс разрабатывает сервисы генерации и публикации; ежедневные задачи выполняет разрешённая автоматизация/планировщик, а не бесконечный сеанс Codex.
- Чужие Facebook-группы и Messenger нельзя считать доступными для неограниченного автоматического постинга и холодной рассылки.
- Оценивать качество каналов по настоящим публикациям заказов и выбору исполнителя, а не только охвату.

## 8. Управление изменениями ТЗ

Документ **не заморожен навсегда**. Он должен меняться, когда появляются новые требования, рыночные данные, проверенные ошибки или ограничения API/законов.

**Версии:**

- `MAJOR`: поменяли ключевой продуктовый принцип, порядок обязательных релизов или архитектуру.
- `MINOR`: добавили/удалили этап, подэтап, важную функцию, новую обязательную зависимость.
- `PATCH`: уточнили критерии, исправили текст, ссылки, тестовые команды без изменения смысла.

**Процедура:** предложение → причины/эффект → затронутые `REQ-*` → изменения этапов/зависимостей → миграции и rollback при необходимости → согласование → PR → новая версия → запись в журнал изменений. Завершённый этап не объявлять незавершённым задним числом без фиксации нового требования или регрессии.

### 8.1. Открытые решения для будущих этапов

- Какой платёжный провайдер подходит к юридической форме бизнеса в Израиле — определить перед этапом 12.
- Flutter или React Native — утверждение через ADR в 11.1.
- Telegram исключён ADR-0001; для 03.7 нужен только безопасный cleanup поля `User.telegram_id` после проверки схемы и тестов.
- Какой вариант доставки чата оптимален для VPS — после проверки нагрузки в 07.2.
- Какие PSEO страницы реально имеют органические посещения — только по HTTP, индексам и данным Search Console.
- Какую степень автономии разрешать публикациям/сообщениям Meta — только после получения нужных прав и проверки правил платформы.
- После пилота статей 14.4 — стоит ли включать Q&A 14.5–14.7: `GO/NO-GO` по качеству, спросу и нагрузке модерации.

## 9. Критерий общего завершения программы

ZemiPro можно считать полноценно реализованным по этому плану, когда:

1. Django-сайт с каталогом всех направлений и двумя путями заказа стабильно работает в Израиле на RU/EN/HE, включая RTL.
2. Заказы, отклики, назначение мастера, чат, отзывы, уведомления, жалобы и приватность подтверждены тестами и реальными сценариями.
3. Для подтверждённых legacy URL приняты и проверены точные решения KEEP/301/404/410 без импорта PSEO-кода, текстов или баз.
4. Органическое продвижение и аналитика помогают принимать решения по реальным показателям заказов.
5. Мобильные приложения используют общий API, а монетизация внедрена **лишь если подтверждена бизнес-гипотеза**; отсутствие дохода не разрешает автоматически объявлять коммерческую модель успешной.
6. Эксплуатационные процедуры, резервные копии, безопасность и обновление этого документа продолжают работать после первого релиза.
7. Обязательный этап 14 закрыт по всем 11 подэтапам; функции, не получившие `GO` на публикацию, проверены и безопасно выключены feature flags.

> **Итог:** разрабатываем ZemiPro по шагам на существующем Django без импорта удалённого PSEO и Telegram; старые URL рассматриваются отдельно.
