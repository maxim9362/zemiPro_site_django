## 3. UX-карта: сценарии пользователей (текущее и целевое движение)

### Гость

Главная → категории/поиск → фильтры → безопасный профиль → (а) приглашение мастера к своей заявке или (б) создать новую заявку → вход/регистрация → подтверждение обязательного email → заказчик. Гость может изучать опубликованные анкеты, но не видит приватные заказы/чат, не отправляет предложения и жалобы без разрешённого входа. Цель редизайна: две различимые главные CTA — **«Найти мастера»** и **«Разместить заявку»**, текст «работаем в Ашдоде», без обещания других городов и запроса адреса.

### Заказчик

Кабинет → создать заявку → 1 категория/услуга → 2 вопросы → 3 Ашдод + способ → 4 срок → 5 бюджет → 6 описание/фото и права видимости → 7 настройки связи → 8 предпросмотр и подтверждение → статус опубликовано → отклики/приглашения → сравнение цен и рейтинга → приватный чат → выбор одного мастера → согласование версии условий второй стороной → assigned → in_progress → результат работы → **явное подтверждение заказчиком** → completed → один отзыв → возможная жалоба/апелляция. Отмена/спор/ошибки/возврат к черновику — отдельные ветви, но не дополнительные статусы из дизайна. Не терять введённое при ошибке и на «Назад».

### Специалист

Email/Google вход → профиль мастера (черновик) → опубликованная анкета/фото → приглашение или подходящая заявка → предложение/редактирование → чат → выбор заказчиком → согласование версий → старт работы только назначенным специалистом → отправить результат → ожидать явного завершения заказчиком → ответить на отзыв (один раз). Неподходящая услуга, неопубликованная анкета, неактивный аккаунт и отклонённое предложение — объяснимые server-derived состояния, а не новые разрешения.

### Модератор

Вход разрешённого staff → очередь жалоб и апелляций → безопасный просмотр цели (включая приватное сообщение **только при подтверждённом доступе**) → решение/отклонение → аудит/уведомление → при разрешённой апелляции отдельное решение. Общая публичная навигация не должна давать доступ в staff-экран; скрытие ссылки не заменяет server-side permission.

## 4. Предлагаемая информационная архитектура (ТРЕБУЕТ СОГЛАСОВАНИЯ)

1. **Общий верхний уровень:** логотип → «Найти специалиста» → «Услуги» → «Разместить заявку» → RU/EN/HE; понятная метка «Ашдод» (не селектор новых городов). Вход/регистрация гостю; пользовательское меню авторизованному. Mobile: компактное открываемое меню, клавиатура/escape/focus, корректный RTL, без 13 постоянно видимых ссылок.
2. **Навигация заказчика:** «Мои заявки» (черновики, активные, выполненные), «Избранное», «Переписка», «Уведомления», «Профиль и приватность». Явная возможность перейти к роли специалиста через существующий POST switch-role.
3. **Навигация специалиста:** «Подходящие заявки», «Мои предложения», «Приглашения», «Переписка», «Уведомления», «Анкета и портфолио»; роль видна в кабинете. Не изобретать отдельные маршруты API ради меню.
4. **Модератор:** отдельная ссылка «Очередь модерации» только если у вошедшего есть фактическое разрешение (проверку в Python, не имитировать JS); внутри очереди жалобы и апелляции.
5. **Шаблоны и компоненты:** base/layout, навигация, breadcrumbs, alerts/live feedback, empty/error/permission state, form-field/error summary, card worker/order/offer, status badge, paginator, wizard progress, chat bubble/attachment, notification item, confirmation pattern. Только Django templates + CSS variables + небольшие JS-модули. Любые новые UI состояния должны отображать **существующий серверный статус**.
6. **Основные экраны в порядке важности:** (а) главная и поиск; (б) безопасный профиль; (в) мастер заявки; (г) кабинеты и заказ/предложения; (д) чат и уведомления; (е) жалобы/модерация. Остальные маршруты сохраняются до отдельного согласованного изменения.

| Репутация/модерация | Ещё нет оценок, отзыв оставлен, ответ мастера, жалоба создана/рассмотрена/отклонена, апелляция недоступна/доступна/решена, нет очереди |

Кнопки недоступных действий не должны обещать исполнение: объяснять причину или скрывать согласно серверному разрешению. Защита не должна полагаться на disabled/hidden в HTML. Сохранять CSRF, PRG/idempotency, server-side валидацию и проверку доступов.
