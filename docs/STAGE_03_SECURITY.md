## Authorization and attack surface

- **One account** can be a client or worker; `active_role` is a dashboard preference only. The user's logged-in session, object ownership, staff permissions and persisted `is_active/is_blocked` govern operations. No client-supplied `user_id`, `profile_id`, `worker_id`, `is_staff`, `role`, `is_verified` or moderation action may grant additional rights.
- `BlockedAccountMiddleware` executes after `AuthenticationMiddleware`; already-authenticated `is_blocked` users are denied all private actions and data pages with 403, except logout and a restricted, read-only public catalog. `is_active=False` users are rejected by Django's existing session/login backend. Marketplace services and moderation service verify persisted account state (not just a possibly stale in-memory user instance). Normal public catalog retains Ashdod-only and published-worker filters. No blocked user obtains order address/phone, staff status or worker publication through role switching.
- Order private details remain owner/assigned worker/staff only, with a separate active/unblocked guard. Clients cannot create or manage another user's order by spoofing IDs; workers cannot respond to own orders, unavailable worker records or blocked accounts. Portfolio and favorites retain their earlier owner-only checks and private image behavior. CSRF remains required for writes.

## Dedicated moderator permissions and immutable decision trail

- Permissions generated by migration (not automatically granted to ordinary registered users): `moderation.review_complaints` to resolve/dismiss complaints, `moderation.moderate_accounts` to block/unblock ordinary accounts, `moderation.review_privacy_requests` to mark an export/erasure request processing or rejected. A staff account **must** separately possess the relevant permission; the service re-reads the actor and permission with a transactional row lock before every decision. The user cannot be their own moderation actor; staff/superuser targets cannot be blocked by the ordinary action.
- `ModerationEvent` stores only actor ID, target ID, optional complaint/request ID, action code and timestamp. No token, raw address, customer phone, uploaded file, free-text complaint, audit note or private account profile is copied. Migration `moderation.0003_moderation_event` installs a PostgreSQL trigger rejecting UPDATE/DELETE as well as a read-only admin view. FK `PROTECT` retains audit actor/target references and avoids silent cascade loss.
- Django Admin complaint status and privacy status are read-only except for audited, permission-scoped actions. A privacy request being *processing* or *rejected* is **not** legal fulfillment or automatic deletion/export: `COMPLETED` is not set by this flow. Admin change/delete of historical Order, Response, Rating and client/worker profiles is disabled. Staff user changes/deletes are restricted; normal moderator action is not a general account-edit permission. Operator must explicitly grant specialized rights to trusted staff; no privilege grants are performed by migrations.
- `marketplace.0007_protect_worker_history` protects `Response.worker` and `Rating.worker` with `PROTECT`. `moderation.0004_protect_complaint_reporter` protects `Complaint.reporter`. Historical `Order.client` was already `PROTECT`. No data migration or real-user deletion is included. Check a restored historic database with proper backup/rollback before owner-approved production rollout.
