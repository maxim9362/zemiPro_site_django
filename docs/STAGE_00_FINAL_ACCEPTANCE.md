## 3. Единый план проверки (Codex Cloud или изолированный локальный runner)

Никаких production-контейнеров, настоящей БД, live DNS, ключей или исходных персональных данных. Проверять только `stage-00-audit`.

1. Из корня checkout: `git diff --check`; `python -m unittest discover -s scripts/tests -p "test_*.py" -v`; `python scripts/stage00_static_diagnostics.py`; `python scripts/stage00_secret_audit.py --history-paths`. Отчёты не должны содержать значений ключей. **PASS засчитывать только по реальному запуску.**
2. В `zemipro_web/` с Django 5.1.x и выделенной PostgreSQL: `python manage.py check`, `python manage.py check --deploy` при безопасных `DEBUG=False`/секретах/hosts, `python manage.py makemigrations --check --dry-run`, `python manage.py migrate --plan`. Применить `migrate` только к новой тестовой БД.
3. Прогнать тесты `accounts` и `marketplace`, затем необходимый полный suite. Покрыть анонимные POST, чужие заказы/контакты, собственные отклики, блокировки, `select_for_update`, уникальности и отсутствие дубликатов.
4. При доступном Docker проверить изолированный Compose/staging smoke. Не подключаться к production или реальным Telegram/PSEO системам.
5. В отдельной фиктивной PostgreSQL запустить `scripts/stage00_pg_snapshot.py` для `zemipro_fixture_*` → `zemipro_restore_*`, подтвердить SHA-256, схему и counts. Скрипт специально не работает с production.
6. По `docs/SEO_URL_INVENTORY.csv` проверить HTTP/GSC при доступности; решения о redirect только для релевантных новых страниц, не массово на главную.
7. Исправить обнаруженные ошибки в этой же ветке. Согласовать конфликт документации с PR #5, зафиксировать объективные PASS/FAIL и лишь затем подготовить **один итоговый PR этапа 00**; merge — после разрешения владельца.

## 4. Внешние блокеры и ограничения

- Удаление PSEO на GitHub **не отзывает старые API-ключи** и не выключает автоматически ранее развёрнутый сайт.
- Основной репозиторий публичен. Прежний SOCKS5 URI с учётными данными сохранился в истории/main. Не выводить его, не выполнять history rewrite или force-push без отдельного решения и без предварительного отзыва ключа.
- Новому Django нужны свои защищённые `DJANGO_SECRET_KEY` и `DB_PASSWORD`. Не удалять их.
- В этом подготовительном шаге **не выполнялись** Django/PostgreSQL/Docker, backup/restore, действия с внешними ключами и production. Синтетические тесты инструментов не эквивалентны интеграционным тестам платформы.

**Заключение:** GitHub-документация и статический обзор подготовлены; весь этап 00 остаётся `IN_PROGRESS` до получения проверяемых результатов и решения по ключам.
