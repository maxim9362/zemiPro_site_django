# ZemiPro — прекращение поддержки Telegram и удаление legacy runtime

**Дата:** 2026-11-10  
**Ветка:** `stage-00-audit`  
**Статус:** `CODE_REMOVED_IN_BRANCH / NOT_MERGED / HISTORY_RETAINS_OLD_DATA`

## Принятое владельцем решение

Telegram и старый PostgreSQL бота больше не нужны для ZemiPro. Новая платформа развивается на существующем Django/PostgreSQL в `zemipro_web/`. Legacy API-токены, SOCKS5-прокси, Telegram-обработчики и отдельный Docker-контур исключаются из рабочей ветки.

## Что исключено из текущего дерева ветки

Удалены 28 отслеживаемых файлов: Python-скрипты старого бота и его админ-бота (`main.py`, `admin_bot/`, `customer/`, `executor/`, `categories/`, `menu/`, `db.py`, `config.py`, `user_status.py`), старые `Dockerfile`, `docker-compose.yml`, корневые `requirements.txt`, `.env.example`, `.dockerignore` и `tests/test_business_logic.py`.

**Никакие файлы каталога `zemipro_web/` не удалялись.** В Django остаётся поле `accounts.User.telegram_id` как часть существующей схемы/миграций: это поле **не ключ доступа**; удалять его только контролируемой Django migration в соответствующем этапе, после проверки реальных данных и совместимости.

Файл `TECHNICAL_REPORT.md` остаётся историческим техническим описанием; любые ссылки в старой документации на Telegram — исторический контекст, не целевая архитектура.

## Что не означает удаление

- **Git main и история не переписаны:** старые ключи, включая прежнюю жёсткую конфигурацию SOCKS5, могут сохраняться в истории публичного репозитория. Исключение файлов из новой ветки не является ротацией.
- Старый работающий сервер, контейнеры, тома/БД, пароли и внешние аккаунты не затрагивались.
- Без подключения к провайдерам невозможно отозвать Telegram Bot API-токены, старые ключи Gemini, сервисную учётку Google и пароль прокси. Их нужно отозвать по месту выпуска; можно отказаться от самих интеграций.
- Прежняя PostgreSQL-база Telegram не удалялась с сервера. Ее конфигурационные файлы удалены лишь из Git-ветки; нет разрешённой/проверенной операции удаления живых БД.
- Код нового Django продолжает использовать **свой** `DB_PASSWORD` и `DJANGO_SECRET_KEY`: их нельзя удалять как класс переменных, даже при отказе от старой системы.
