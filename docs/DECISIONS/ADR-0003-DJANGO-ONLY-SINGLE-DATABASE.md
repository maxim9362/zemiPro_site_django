# ADR-0003 — единая Django/PostgreSQL архитектура и первый выпуск

**Дата:** 2026-11-10  
**Статус:** ACCEPTED — архитектурное решение для планирования; деплой не разрешён  
**Область:** подэтап 00.5; решения 00.1–00.4, ADR-0001/ADR-0002

## Контекст

В основном репозитории уже существует `zemipro_web/` с Django-приложениями, пользовательской моделью, миграциями и сервисами. Отдельно есть исторический aiogram/asyncpg Telegram и Flask/PSEO/SQLite. Владелец исключил Telegram как канал и Flask/PSEO как платформу; от PSEO может быть полезен только **список старых URL**. Текущий публичный сайт, продакшен-схема БД и фактические данные не исследованы до достаточного для миграции уровня.

## Решение

1. **Один исходный код продукта:** сохраняем и развиваем существующий Django в `zemipro_web/` основного репозитория, не создавая новый параллельный backend. Новые HTML-макеты заказчика/мастера, mobile/desktop реализуются отдельно поверх того же сервера и доменной логики.
2. **Одна транзакционная система учёта:** Django ORM + PostgreSQL для `accounts`, `marketplace`, `locations`, `notifications`, `moderation`, `analytics` и будущих `chat`/SEO-сущностей. Применение schema changes — только Django migrations. Тестовая и staging БД физически отделены от production (не "одна общая БД" для всех окружений).
3. **Одна модель личности:** `accounts.User` и связанные профили, без второй базы пользователей. В текущем коде `User.role` поддерживает один выбор; возможность одновременного заказчика и мастера решается в 03.1 без клонирования `User`.
4. **Нет импорта старого Telegram/PSEO:** ничего из `db.py`, бот-аккаунтов, заказов, CSV/SQLite PSEO, текстов и генераторов в целевые таблицы не переносить. Исключение — `docs/SEO_URL_INVENTORY.csv` как список URL для анализа, а не база данных Django.
5. **Справочники новой платформы:** использовать существующие Django `Category`, `Subcategory`, `City` и seed-команды как отправную точку. Состав категорий и переводы уточнить в 02; *не* копировать автоматически старые PSEO/Telegram словари. Новая версия каталога проходит проверку смыслового соответствия, RU/EN/HE и RTL.
6. **SEO и домен:** `apps.seo` сейчас заготовка. Новые Django-страницы создать по актуальному ТЗ без Flask. Старые URL `/master/...` оставить в реестре с решением `REVIEW` до подтверждения Search Console, HTTP и эквивалентности. Конкретные 301/404/410 — только после утверждения матрицы и тестов этапа 08; никаких автоматических перенаправлений на главную.
7. **Секреты/сохранность:** блокер 00.2 и отсутствие подтверждённого восстановления 00.3 запрещают выпуск/перенос рабочих данных. Нельзя автоматически переиспользовать production DB, volume, медиа, адреса или контакты.
8. **Первое развертывание:** сначала независимый staging на проверенной конфигурации 01.1, изолированной PostgreSQL и синтетических данных, HTTPS и проверках. Развертывание на основном домене разрешается отдельно после этапа 08, backup/restore, проверки URL и плана отката. `zemipro_web/docker-compose.django.yml` — имеющийся пример, не доказательство рабочей production-конфигурации.

## Границы данных и доступа

- Только авторизованный заказчик создаёт `Order`; `Order.client` — обязательный FK; в `0003_require_order_owner` уже есть безопасная остановка при старых `client=NULL`. Самостоятельно не назначать владельцев и не удалять legacy-строки.
- Свободный текст заявки, точный адрес и телефон не публикуются. Для контакта выбранного мастера использовать защищённый чат будущего этапа 07; заказчик самостоятельно решает, какие приватные данные сообщить. Доступ к данным и операциям ограничивать owner/assignee/staff, включая будущий API.
- До отдельного решения монетизация выключена: никаких платежей за услуги, за отклики или доступа к контактам.
- RU/HE/EN, RTL и четыре утверждённых варианта интерфейса — потребители тех же Django-сервисов, а не четыре независимые базы.

## Отложенное согласование старых формулировок

Исторические версии `docs/DEVELOPMENT_PLAN.md` и `docs/TECHNICAL_SPEC.md` содержали задачи импорта Telegram/PSEO. В v1.3 текущей ветки они синхронизированы так, без сокращения 14 обязательных этапов и 96 подэтапов:
- 02.1: сопоставление нового утверждённого каталога с уже существующими Django-данными, без импорта legacy;
- 03.7: отказ от Telegram, проверка отсутствия зависимостей/безопасный cleanup старых интеграционных точек;
- 08.2: создание нового SEO-каталога и проверка старых URL, без переноса Flask/SQLite/SEO-текстов.
Это документальное уточнение, **не** начало 02/03/08 и не самостоятельное изменение другого этапа.

## Отказ от альтернатив

- Отдельный backend Flask/PSEO — REJECTED, поскольку плодит runtime, пользователей и безопасность.
- Импорт базы Telegram/SQLite — REJECTED по решению владельца и из-за неизвестной идентичности пользователей/полноты данных.
- Создание новой пустой Django-архитектуры вместо развития существующей — REJECTED: сохраняем действующие модели, тесты, миграции, защищённые сценарии.
- Переключение публичного домена в этапе 00 — REJECTED: нет подтверждённого backup, инвентаризации и разрешения.

**Проверки 00.5:** независимая сверка моделей, URLconf, миграций и Docker-конфига; clean migrations и backup/restore на synthetic PostgreSQL прошли. GSC, реальные базы и production не проверялись.
