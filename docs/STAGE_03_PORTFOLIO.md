## Stored model and access controls

- Existing `accounts.WorkerProfile` remains the only specialist/company profile. New add-only `accounts.0009_worker_portfolio` creates `WorkerPortfolioPhoto` with `worker` FK (`PROTECT`), `file_key`, caption (max 300), `sort_order` (0–999), `is_public=False`, `rights_confirmed_at`, and creation time. No migration copies or automatically publishes legacy content. `PROTECT` prevents accidental cascade removal of a worker profile with stored work samples; legal erasure remains a separately reviewed workflow.
- Owner uploads through `POST /accounts/worker/portfolio/add/` after authentication/CSRF. `GET /accounts/worker/portfolio/` lists only the signed-in worker's media. Only the owner can change caption/order/visibility or delete through POST `.../<id>/edit/` and `.../<id>/delete/`. Request `worker_id`/`user_id` never selects the acting owner. Blocked/inactive users cannot modify media. All new POST endpoints use Django's existing session/CSRF protection.
- `GET /accounts/worker/portfolio/<id>/image/` does not redirect to storage or expose the path. It streams a normalized `image/jpeg` with `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`; any unrelated request to a private/invalid key returns 404. Public access additionally requires both `photo.is_public` and an active, unblocked, explicitly published worker permitted by the first pilot's Ashdod public-worker queryset. Draft photos are owner-only even if their parent worker is published; an unpublished/blocked/off-pilot worker's photos never become public by guessing IDs.

## File validation and privacy

- Runtime image decoder pinned to `Pillow==13.0.0`; only JPEG/JPG, PNG and WebP supported. File extension, declared MIME and actual decoded image format must agree. Strict upper limits: **5 MiB original bytes**, **12 megapixels**, **1600 px max output side**, **10 work samples per worker**. Animated files and unsafe/unreadable content are rejected; truncated or mismatched input cannot be stored. No SVG, HTML, PDF, executable or archive upload is allowed.
- After verifying the content, the server applies EXIF orientation, converts to RGB (white background for transparency) and independently re-encodes to JPEG. Original EXIF/GPS/ICC/XMP/comment chunks and original filenames are never preserved or served. Server-generated opaque `worker-portfolio/<uuid>.jpg` keys prevent upload path traversal and name collisions.
- `ZEMIPRO_PRIVATE_MEDIA_ROOT` is separate from `MEDIA_ROOT` and `STATIC_ROOT`, fail-closed when configured within a publicly served media/static root. The original file and private storage keys never appear in templates. Local filesystem permissions are file 0600, directories 0700. Private media must **not** be mapped to `/media/` by Django's debug helpers or a reverse proxy.
- The uploader confirms the right to share the photo. Public listing identifies it as an example supplied by the specialist, **not proof of independently verified work**. No automatic verification badge, claims about actual completed work or paid storage/provider integrations.

## Operational caveats and release gates

- Before publicly accepting real uploads: provision a persistent and private storage volume, web-server upload-body limit, disk space quotas/monitoring, antivirus/media threat process as appropriate, secure off-host backup and verified restore. Evaluate orphan-file cleanup if an **outer** database transaction rolls back after the file was persisted; current service cleans up on immediate DB errors and deletes files only after successful DB deletion commit. Do not assume the default container filesystem is durable. Set up owner-approved secrets and server permissions.
- Account export/erasure requests remain requests for manual handling; do not silently erase active orders or retain files beyond the approved retention plan. Ensure retention, rights declarations, and incident/reporting practices have legal/owner acceptance before public publication.
