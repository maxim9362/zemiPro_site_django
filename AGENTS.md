## 1. Контекст проекта

**ZemiPro** — универсальный маркетплейс услуг Израиля по функциональной модели [Profi.ru](https://profi.ru/), но с собственным кодом, дизайном, брендом и контентом. Основная платформа — **Django + PostgreSQL**; сначала адаптивный сайт, затем Android/iOS через единый API. Все категории услуг, языки `ru/en/he` (иврит с RTL); **единственный город первого публичного пилота и первоначального продвижения — Ашдод**; любые другие города — только после отдельного разрешения владельца и расширения серверного ограничителя. Все 25 записей технического справочника сохраняются в БД и не означают 25 городов запуска. Клиент создаёт заявку или ищет мастера; мастер откликается, общается и получает отзыв. Базовые сценарии бесплатны при запуске; монетизация — отдельное решение. Не вводить обязательную проверку лицензий платформой при регистрации; не выдавать неподтверждённые статусы, соблюдать применимое право.

## 2. Рабочий процесс GPT → Codex Cloud и экономия лимитов

Владелец утвердил разделение ролей:

- **Реализация через GPT в ChatGPT:** анализ отдельного этапа и подэтапов, код и документация, работа в существующей ветке этапа, адресные статические и доступные локальные тесты, подготовка единственного итогового PR.
- **Итоговая независимая проверка через Codex Cloud:** после завершения всех подэтапов этапа — code review, сверка с ТЗ, архитектура и безопасность, Django/PostgreSQL migrations, интеграционные и необходимые регрессионные тесты, Docker/configuration по требованиям этапа, документация и гейты.
- Найденные при итоговой проверке ошибки исправляются **в той же ветке этапа**; Codex повторяет только необходимые проверки. Полный аудит перед каждым подэтапом не выполняется.
- Один этап = одна существующая рабочая ветка = один итоговый PR. Не создавать PR на каждый подэтап и не смешивать изменения разных этапов.

1. **Минимальный контекст:** перед работой прочитать этот файл, относящиеся к задаче разделы `docs/ROADMAP.md`, `docs/DEVELOPMENT_PLAN.md`, `docs/TECHNICAL_SPEC.md` и лишь затрагиваемые файлы. `docs/PROGRESS.md` и специализированные документы открывать по необходимости. Если файл ещё не добавлен в GitHub, не делать вид, что прочитан: сообщить и использовать только подтверждённые данные.
2. **Без полного аудита на каждом шаге:** не перечитывать весь код, GitHub, историю веток, PR и все документы. Полный аудит — по отдельной команде или при конкретном критическом риске. Не повторять уже подтверждённые проверки без причины.
3. **Узкий scope:** работать строго в заданном этапе и подэтапе `XX.Y`. Перед правками определить затронутые модули, совместимость, риски, нужные тесты. Не делать несвязанный рефакторинг, перестройку каталогов и дополнительные функции.
4. **Один этап — одна ветка — один итоговый PR.** Все подэтапы проходят в одной ветке с промежуточными коммитами. Не открывать отдельный PR для каждого подэтапа и не дублировать существующий. Исключения — только по команде владельца.
5. **Документация после каждого подэтапа:** обновлять *только релевантные* записи `docs/PROGRESS.md`, `docs/ROADMAP.md`, изменённые требования и контракты. Не ждать закрытия этапа и не переписывать большие документы целиком.
6. **Адресные тесты:** GPT запускает доступные проверки изменённого поведения во время подэтапа; полный необходимый набор и независимая проверка Codex Cloud выполняются после завершения всего этапа или раньше по критическому риску. Не экономить на обязательных проверках безопасности.
7. **Модель/reasoning:** модель Codex выбирает пользователь; Codex не переключает модель, не изменяет настройки reasoning и не предлагает автоматического выбора. Не требовать повышенного reasoning для простых задач — экономить за счёт чёткого задания и узкой области.
8. **Fast mode:** не включать и не предлагать включение по умолчанию; оставлять настройки владельца без изменений.
9. **Краткие ответы:** результат подэтапа — несколько фактов о коде, проверках, документации, PR, блокерах. Без повторных длинных аудитов. Не выдумывать числовые «официальные лимиты» токенов или запросов.

**Приоритет: безопасность и качество → проверяемость → экономия лимита → скорость.**

## 4. GitHub, статусы, приёмка

- Начинать этап и переходить на следующий **только по команде пользователя**. Не изменять `main` напрямую, не объединять PR самостоятельно.
- Статусы: `NOT_STARTED`, `IN_PROGRESS`, `BLOCKED`, `REVIEW`, `DONE`, `DEFERRED`; при необходимости отдельно `IMPLEMENTED`, `MERGED`, `LOCALLY_VERIFIED`, `DEPLOYED`, `ACTIVATED`. **Код написан ≠ тесты пройдены ≠ PR объединён ≠ сайт развёрнут.**
- Подэтап `DONE` — только при выполненных критериях, соответствующих тестах и документации. Этап `DONE` — после всех критериев, проверок, подтверждённого принятия PR. Не считать старый код готовым без проверки.
- За пределы утверждённого `XX.Y` не выходить. Новые требования/изменение порядка согласовать, обновить ТЗ и roadmap, сохранить журнал решений.
- Сохранять пользовательские изменения и совместимость; не делать force-push, destructive reset, удаление данных, пересоздание инфраструктуры без отдельного разрешения.

## 5. Архитектура и локализация

- **Только зарегистрированные заказчики создают и изменяют заказы.** Гости просматривают каталог; анонимные POST не должны создавать `Order`. `Order.client` обязателен, права owner/assignee/staff проверяются на Django-сервере и в будущем API, а не только скрытием кнопок.

- Развивать **существующий** Django внутри `zemipro_web/`; бизнес-логика общая для HTML/HTMX и будущего версионированного DRF API. Не создавать второй Django-проект или микросервисы без обоснования.
- Уважать текущие границы `accounts`, `marketplace`, `locations`, `seo`, `notifications`, `moderation`, `analytics`; новое приложение создавать лишь когда оно действительно нужно.
- **PostgreSQL** — основная БД. Схема изменяется только через **Django migrations** (не Alembic из Fonbet); миграции тестировать на изолированной БД. Не менять production-схему по факту создания миграции.
- Локализация: полные `ru/en/he`, RTL для иврита, проверка маршрутов, SEO и форм; тексты пользователей хранить в оригинале, AI-перевод маркировать. Не выдавать автоперевод за цитату автора.
- Для интерфейса — `Asia/Jerusalem`; внутренние timestamps — timezone-aware UTC. Проверять переходы DST, где существенно.
- Не добавлять новые платные сервисы, Redis, очереди, поисковые движки или AI-зависимости «про запас». Gemini не должен быть обязательным для основной операции заказа.

## 6. PSEO, SEO и работа с живым сайтом

- **Не ломать существующие адреса.** До миграции составить реестр реально работающих SEO-URL с источником и решением: сохранить адрес, перенести контент или сделать точный `301`. Проверять canonical, hreflang, sitemap, robots, внутренние ссылки и мобильную доступность.
- **Старый PSEO удалён**; код, тексты, категории и SQLite не импортируются. Сверять только подтверждённые публичные URL из `docs/SEO_URL_INVENTORY.csv` по HTTP/GSC, создавать точные KEEP/301 при реальной эквивалентности.
- Не генерировать массово пустые/однотипные SEO-страницы, фальшивые предложения, цены, отзывы или анкеты мастеров.
- Изменения домена, DNS, production Nginx, robots, массовые 301 и переключение Flask/PSEO → Django — **только по отдельному разрешению владельца**, с проверенным откатом.

## 7. Безопасность и реальные действия

- Наследие содержит потенциально раскрытые секреты: `.env` и JSON ключ прежде хранились в **бывшем приватном PSEO** (репозиторий удалён владельцем); SOCKS5 с учётными данными присутствовал в **публичном основном Git**. Удаление файлов/репозитория не отзывает ключи и не очищает историю. Проверить/отозвать действующие старые ключи; **не печатать значения**, не копировать в коммиты, логи и тесты.
- Секреты и `.env`, сервисные JSON-ключи, дампы, SQLite/PostgreSQL data files, реальные контакты, адреса, переписки и финансовые сведения — не коммитить. Перед PR проверять diff/ignore. Настройки получать из окружения; безопасные примеры — в `.env.example`.
- Публично не показывать домашние адреса, телефоны и приватные чаты без основания. Проверять объектные права на сервере в Django views, API, WebSocket и медиа. Нельзя полагаться на скрытие кнопок в UI.
- Анонимные заявки запрещены. После входа сервер назначает `Order.client` из текущего пользователя; идентификатор объекта не является разрешением, объектные права проверяются для каждого чтения и изменения.
- Никаких фиктивных бейджей «проверенный специалист», отзывов, выполненных заказов и гарантий. Отсутствие проверки документов не отменяет требований законодательства Израиля.
- Сетевые операции: разрешённый доступ, тайм-ауты, лимиты частоты, ограниченные повторы; не обходить CAPTCHA, `403/429`, авторизацию и антибот-защиту.
- Не отправлять массовые холодные сообщения, не публиковать от имени бренда через неподдерживаемые API, не создавать фейковые аккаунты. Публикации/ответы — только через разрешённые интеграции и согласованную политику.
- **Реальные платежи, рекламные траты, рассылки, секреты, производственные БД, VPS, DNS и удаление пользовательских данных требуют отдельного разрешения.**

## 8. Проверки и разделение сред

**Во время подэтапа:** целевые тесты изменённого поведения; `git diff --check`; для Django-кода по возможности `python manage.py check`; после изменения зависимостей или при приёмке — `python -m pip check`. Факты обозначать `PASS/FAIL/SKIP/NOT_RUN`, а не «всё работает» без запуска.

**Перед закрытием этапа:** обязательные интеграционные проверки, безопасность и права доступа, совместимость схемы/миграций, `ru/en/he`, важные SEO-маршруты, защита от дубликатов и ошибок фоновых задач. Полный набор прогонять там, где это требует риск/критерий приёмки. Production-данные для destructive tests не использовать.

Метки выполнения: `CODEX_CLOUD` (изолированный код, fixtures, PR, без production-доступа), `LAPTOP_LOCAL_CODEX` (локальная тестовая PostgreSQL), `HYBRID_ACCEPTANCE` (облачная реализация + локальная проверка), `VPS_OPERATOR` (действия на сервере с разрешением). **Merge PR ≠ deployment ≠ activation.** Для production нужны проверенный backup/restore, план отката и подтверждение владельца; соседние службы сервера не затрагивать.

## 9. Документация и итог после каждого подэтапа

Точечно обновить `docs/PROGRESS.md`, статус в `docs/ROADMAP.md`, затронутые требования и контракты; журнал изменений маркетинга/SEO — только если их действительно меняли. Формат короткой записи:

```text
Подэтап: XX.Y; статус: ...
Сделано/переиспользовано: ...
Файлы/миграции: ...
Тесты: PASS ..., FAIL ..., SKIP ..., NOT_RUN ...
Ветка, commit, PR, merge: ...
Реальная БД/VPS/публикации: не затронуты (или указать подтверждённое действие)
Блокеры/риски: ...
Следующий разрешённый шаг: ...
```
